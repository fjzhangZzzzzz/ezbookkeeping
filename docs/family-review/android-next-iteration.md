# Android 下一轮需求与改进清单

本清单基于已提交的 Android 搜索、设置、家庭总览和性能改造整理。它区分
“代码已实现”和“发布前证据已完成”，避免把本地构建通过误认为真实设备验收。

## P0：发布前必须补齐

1. 使用已认证的 QA 账号和代表性数据，在真实 Android 设备测量：
   - 冷启动进入记账页；
   - 搜索首次打开、搜索提交、切换标签页后再次进入；
   - 家庭页首次打开、切换月份、切换成员、加载更多；
   - 秒开开启/关闭、保存成功/失败和草稿恢复。
2. 按实际发布配置复测 SQLite 家庭聚合查询：使用与发布环境一致的 SQLite
   版本、连接数和数据文件，并记录 EXPLAIN、p50/p95、内存、锁等待和超时。
3. 做一次发布前 Android 包验收：versionCode、签名、包名、APK、`update.json`
   和 `SHA256SUMS`，并使用独立 Android Release tag。

## P1：下一轮优先改进

- 补齐搜索和家庭总览的 API 契约测试，覆盖日期边界、退款负值、外币、家庭内部转账、
  分类/标签同名、并发写入和搜索期间数据变化。
- 明确搜索缓存失效策略：记账、修改、删除、登出、切换账号后必须清理或刷新缓存。
- 评估搜索摘要接口与首屏列表是否重复计算 `totalCount`；在不牺牲金额精度的前提下减少重复查询。
- 完成钱迹 APK 对照表：入口层级、筛选项、默认值、空状态、加载态、错误态、返回行为和设置分组。
- 补齐无网络、接口超时、401 刷新失败、服务端旧版本不支持新接口时的降级文案。

## P2：可以延后

- 进一步优化十并发百万级 SQLite 延迟。当前产品目标为两人正常同时使用，现有单请求性能和并发零错误已经足够；除非未来扩大用户规模，不建议为此牺牲 SQLite 单连接写入稳定性。
- 增加更细的 UI 性能埋点、长列表帧率和内存曲线。
- 统一无障碍语义、字号放大、深色主题和多语言文案的最终巡检。

## 建议下一步

先完成 P0 真机和 SQLite 发布配置验收；若没有阻断项，再按钱迹对照表处理 P1。P2 不进入当前发布阻塞条件。

### 最小实现边界

不建设家庭创建/邀请/角色/授权平台，不引入Redis、任务队列或独立统计服务。成员使用现有用户及停用状态，管理员复用应用CLI管理，补齐停用后的会话吊销与家庭缓存失效步骤；10人上限在开通流程校验。

字典是实例级共享资源，由一个集中服务负责列表、引用可用性、写入、删除引用检查。其存储所有者不能是某位普通成员，也不能把个人数据查询的uid过滤普遍取消。具体字段映射在阶段0的小型源码设计中固定，不为将来多家庭预留完整模型。

个人账户/交易写服务继续使用self。家庭读服务只读当前启用成员的数据，附件通过真实交易关联读取；不向浏览器签发其他成员具有写权限的普通会话令牌。内部往来使用稳定系统分类标识；这些类别不受成员改名或隐藏影响而改变统计语义。

共享字典涉及所有实际引用入口，包括交易、手动模板、导入导出、初始化、清空数据及注销。关闭自动定时记账后不开发其UI或后台执行，但禁止通过旧接口重新启用。个人导出再导入时不能误覆盖全家字典或自动把内部往来转换成普通收支。

## 2. 部署拓扑

```text
手机 / 浏览器
       │ 公网 HTTPS :443
       ▼
edge-01：现有 Caddy（TLS、反向代理、访问日志脱敏）
       │ EasyTier 私网 HTTP，仅允许准确回源来源
       ▼
control-01：homelab-ezbookkeeping，单应用容器，非root
       ├─ SQLite（本机持久目录，不经网络共享）
       ├─ 本地附件/头像等文件
       └─ 原生OIDC ──HTTPS──► 现有Pocket ID

现有Backrest计划 ── Ansible一致性保护 ── Restic同快照保存数据与匹配工件
现有监控 ── 就绪/HTTPS/重启/磁盘/备份成功状态
```

不在应用外层强制使用Pocket ID forward-auth/oauth2-proxy保护整个站点，否则Pocket ID故障时连账密登录页也可能无法使用。应用自己验证会话，OIDC只是第二种登录入口。仅备份管理页面继续使用其已有管理员保护，不改动其他服务的登录机制。

### 域名与端口建议

建议域名 `books.fjzhang233.top`，属于提议而非已创建DNS记录；使用独立域名根路径，避免子路径对OIDC和移动路由的额外影响。Caddy统一证书，应用root_url设置为最终HTTPS完整URL。

回源候选端口为control-01的 `10.144.144.2:18882` → 容器8080。18882尚未做实时冲突检查，若已占用则选择同类空闲端口，并只在唯一清单定义。只允许edge-01通过指定私网来源访问，应用不能额外发布到所有宿主网卡，也不开放SQLite端口。Docker端口映射和宿主防火墙/DOCKER-USER等实际生效路径必须一起验证，不能只看UFW或配置文本。

公网只开放既有HTTPS入口，后端回源不加公网直连。应用可信代理设置为实际到达容器的准确代理/网关来源，抓取观测后限定，不能照抄整个10/8或172.16/12。Caddy重建可信转发头，应用保留自身鉴权；公网HTTP仅跳转HTTPS。

## 3. 容器、文件与配置

一个应用容器同时提供现有Go API和前端静态资源，不分离前后端服务。使用项目自己的镜像，先只构建linux/amd64；正式镜像固定版本与digest，不用latest、不在生产现场git pull并构建。发布包保存源码SHA、镜像摘要和依赖锁。优先用现有构建结构，改掉会造成依赖漂移的安装步骤，前端npm ci、Go依赖只读锁定；构建后检查go.mod/go.sum/package-lock.json未被意外改写。

应用代码与业务CI在本仓库；生产配置、部署入口和恢复Runbook在homelab-infra。镜像可发布到fork对应的容器仓库；若控制节点访问仓库不可靠，使用同一准确镜像离线归档及SHA256分发，仍不现场重建替代镜像。

| 宿主路径 | 内容 | 容器用途 |
|---|---|---|
| /etc/homelab/ezbookkeeping/ezbookkeeping.ini | 渲染后的受限运行配置，含必要敏感输入 | 只读挂载，EBK_CONF_PATH指向该文件 |
| /var/lib/homelab/ezbookkeeping/data | SQLite数据库及必要状态 | 可写挂载到/ezbookkeeping/data |
| /var/lib/homelab/ezbookkeeping/storage | 附件/头像等本地文件 | 可写挂载到/ezbookkeeping/storage |
| /var/log/homelab/ezbookkeeping | 应用必要日志 | 可写挂载，轮转且禁敏感正文 |
| /srv/homelab/ezbookkeeping/current | 当前准确Compose/镜像引用及发布依据 | Ansible管理；具体组件布局沿用infra规范 |

沿用镜像的非rootUID/GID（当前Dockerfile为1000:1000，最终依冻结基线确认），提前设置挂载权限；配置只允许必要UID读取。根文件系统尽量只读，必要临时目录tmpfs，移除无关capability、no-new-privileges，日志轮转。资源预算以512MiB–1GiB内存为初始配置评估范围，通过真实导入和图片测试确定；不能把未测数值当成容量保证。

核心配置：SQLite+local_filesystem；强随机独立secret_key；账密和OIDC开；公开注册/OAuth自动注册关；原30天会话及续期；内置图标；自动定时模板与后台生成两个开关都关；AI/MCP/地图默认关。配置须逐项核对冻结版本的键名与行为，不只确认INI可解析。

Caddy限制请求体大小时必须结合账单导入和图片上限，避免过小限制破坏已有个人功能；同时限制不必要大请求。动态API/敏感内容不被共享代理缓存，静态资源按构建hash缓存。CSP/浏览器安全头需与现有Vue/图表/脚本功能实测兼容，不直接复制其他产品的策略。

## 4. Pocket ID与账号开通

在现有Pocket ID通过原生UI/API新建专用OIDC客户端，issuer沿用现行清单（当前为https://auth.fjzhang233.top）。建议回调 `https://books.fjzhang233.top/oauth2/callback`，最终按冻结源码和最终域名确认，准确匹配且启用PKCE S256及issuer/TLS校验。

Client Secret和应用secret_key通过SOPS/受限运行文件管理，不写进Compose、Git、回复或命令历史。不要为了接本应用修改现有Pocket ID用户、签名身份或其他客户端。

关闭两种自动注册，通过应用CLI预建本地账号；成员先用账密进入，再在账号设置中完成Pocket ID绑定。实际验证两入口同一UID、已有账户/交易不分裂、注销只影响本应用、Pocket ID故障账密仍能用、手机正常续期。用户名/邮箱稳定性和OIDC主体键风险按方案核验；未经本地密码确认不得因同邮箱直接接管已有本地账号。

本应用不配置独立管理员角色页面。管理员开通/停用/吊销设备会话使用现有应用CLI/API与Runbook的最少步骤；没有现成安全入口的操作补最小应用CLI能力，而不是直接常态编辑产品数据库。

## 6. 备份、恢复与升级流程

当前Backrest是唯一备份调度与Restic执行入口，依据homelab-infra/docs/runbooks/backrest.md和recovery.md；此前文档仅笼统提到Ansible/Restic，不应据此再建cron或独立timer。当前初始计划每日03:00，实际以Backrest产品配置为准，不为了本应用覆盖已有时间或留存规则。

接入现有平台一致性流程：Backrest触发prepare钩子→记录应用原运行状态并停止写入→检查数据库/附件/配置/镜像/发布必需输入→一次Restic快照→finish恢复原运行状态并核对快照完整性。异常由既有保护机制恢复原状态，不创建另一套协调器。新应用登记必测集合，不以目录存在或备份UI显示成功替代恢复演练。

首次正式记账前做一轮带合成账目和图片的真实备份/隔离恢复验证。隔离实例只挂恢复出的副本，使用独立端口且不接生产数据/公网；本地核验余额、字典、明细、图片、停用和schema版本。真实Pocket ID登录另在获准测试入口或正式切换后验证，不能让隔离测试暗中访问生产身份或让用户误记到测试库。

灾难恢复开放公网前清理恢复出的会话、复核停用成员，再让成员重新登录。密钥、数据与镜像来自同一恢复点，不借现场状态补缺，不清空数据库来绕过失败。RPO24h/RTO1天仍只是现行目标，以本产品演练结果为准；同故障域限制保留。

日常升级：测试与干净源码构建→固定新制品→按infra规范提交/检查/发布配置包→备份→prepare_only→停写并激活→真实业务验收→保留准确回退点。无schema变化且确认兼容可回镜像；schema变化或数据不兼容时恢复旧镜像+同一备份数据/附件/密钥，明确丢弃备份后写入，不把切回image当数据库已回滚。

## 7. 最终上线顺序

1. 完成本地闭环和必要自动化检查，生成不可变候选镜像。
2. 复核control-01/edge-01身份、资源与准确变更；准备受限配置及专用Pocket ID客户端。
3. 在隔离/临时测试数据上验证镜像启动、SQLite、双登录与手机保持登录。
4. 将本应用接入Backrest必测范围，完成备份和隔离恢复。
5. 按准确批准范围配置DNS、回源准入和Caddy；prepare后激活。
6. 创建正式新库及成员账号，验证HTTPS、两种登录、同UID绑定、真实手机记账/家庭查看/CSV。
7. 确认每日计划含应用且端到端成功，再开始正式使用；保留简单缺陷列表，后续只按真实需求扩展。

完整生产验收分开陈述：源码已提交、镜像已发布、infra已发布、已部署、业务已验收、备份已恢复。当前以上均为计划，尚未达到其中任何新增状态。
